# Phase 04.3: Scatter Plot Color-By Selector and Cross-Card Sync - Research

**Researched:** 2026-02-16
**Domain:** Dashboard-level reactive state management and cross-component color synchronization
**Confidence:** HIGH

## Summary

This phase implements a centralized color-by attribute selector that controls data point coloring across ALL dashboard card types (scatter, map, histogram, pie). The key architectural challenge is promoting color-by from a per-card feature (currently only in MapCard) to a dashboard-level concern with shared state.

The codebase already has most building blocks in place: StyleManager handles colors, MapCard has a working color-by dropdown component, and InteractiveDashboard already manages shared state (geometryType, colorByAttribute). The primary work is extracting MapCard's dropdown for reuse, extending color-by logic to non-map cards, and implementing cross-card color synchronization via the existing reactive prop pattern.

**Primary recommendation:** Extend the existing InteractiveDashboard state management pattern (geometryType/colorByAttribute) rather than creating new managers. Reuse MapCard's dropdown component and color logic. Follow the established LinkableCardWrapper pattern for passing color-by state to cards.

### Pattern 1: Dashboard-Level Reactive State

**What:** Use Vue 2.7 Composition API `ref()` in InteractiveDashboard.vue to hold shared state, pass via props to cards.

**When to use:** When state is dashboard-scoped (not global app state, not card-local state).

**Example:**
```typescript
// Source: InteractiveDashboard.vue lines 261-262, 849-856
// Current implementation (already working for MapCard)
data() {
  return {
    geometryType: 'all' as string,
    colorByAttribute: '' as string,  // Initialized from YAML in mounted()
  }
},
mounted() {
  // Initialize from YAML colorBy configuration
  if (this.yaml.map?.colorBy?.default) {
    this.colorByAttribute = this.yaml.map.colorBy.default
  } else if (this.yaml.map?.colorBy?.attributes?.length > 0) {
    this.colorByAttribute = this.yaml.map.colorBy.attributes[0].attribute
  }
}
```

**Why this pattern:** Already proven working for geometryType. Lines 124-125 show event handling: `@update:geometry-type="geometryType = $event"` creates two-way binding without v-model complexity.

### Pattern 3: Color-By Coloring in Cards

**What:** Cards compute colors based on `colorByAttribute` prop using StyleManager.

**When to use:** When rendering data points/bars/slices that need color-by attribute coloring.

**Example (based on MapCard.vue lines 1812-1870):**
```typescript
// In card's computed/render logic
const getPointColor = (dataRow: any): string => {
  if (!props.colorByAttribute) {
    // No color-by: use default theme color
    return StyleManager.getInstance().getColor('chart.bar.default')
  }

  const attributeValue = dataRow[props.colorByAttribute]

  // Detect type from data (per user requirement: auto-detect, not in YAML)
  const isNumeric = typeof attributeValue === 'number'

  if (isNumeric) {
    // Numeric: use sequential scale
    const [min, max] = getDataRange(props.colorByAttribute)
    const t = (attributeValue - min) / (max - min)
    return StyleManager.getInstance().getSequentialColor('viridis', t)
  } else {
    // Categorical: use categorical palette
    const sortedValues = getSortedUniqueValues(props.colorByAttribute)
    return StyleManager.getInstance().buildCategoricalColorMap(sortedValues).get(String(attributeValue))
  }
}
```

**Key insight from MapCard:** LayerColoringManager (lines 62-63) handles complex role-based coloring for maps. For simpler cards (scatter, histogram, pie), direct color assignment is sufficient.

### Anti-Patterns to Avoid

- **Don't create ColorByManager:** State is simple (single string), no observer pattern needed, no coordination logic required. Ref() is sufficient.
- **Don't use Vuex for dashboard-scoped state:** Vuex is for cross-route global state. Dashboard state should be component-scoped.
- **Don't re-register Plotly event handlers on every update:** ScatterCard.vue lines 310-322 show correct pattern: register ONCE in initializeChart(), use Plotly.react() for updates.
- **Don't duplicate color logic across cards:** Use StyleManager methods (buildCategoricalColorMap, getSequentialColor) for consistency.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Color palette generation | Custom color arrays per card | StyleManager.buildCategoricalColorMap() | Ensures consistent colors, alphabetically sorted categories |
| Numeric color scales | Linear interpolation between two colors | StyleManager.getSequentialColor('viridis', t) | Professional color scales (viridis, blues, plasma), perceptually uniform |
| Dropdown component | New dropdown from scratch | Extract MapCard dropdown to shared component | Visual consistency (user requirement), already styled correctly |
| Type detection (categorical vs numeric) | Hardcode in YAML | Auto-detect from data values | User requirement: "auto-detected from actual data values" |
| Legend rendering | Custom legend per card | ColorLegend.vue component | Already implemented, theme-aware, click-to-filter built-in |

**Key insight:** MapCard already solved all these problems (color scales, legend, dropdown, type detection). Extract and reuse rather than rebuild.

## Common Pitfalls

### Pitfall 1: Plotly Event Handler Memory Leaks

**What goes wrong:** Re-registering Plotly event handlers on every re-render causes "MaxListenersExceededWarning" and broken interactions.

**Why it happens:** Plotly.newPlot() clears handlers, but calling `.on()` multiple times adds duplicate listeners.

**How to avoid:** Follow ScatterCard pattern (lines 310-341):
- Use `Plotly.newPlot()` ONCE during initialization
- Register event handlers ONCE after newPlot
- Use `Plotly.react()` for all subsequent updates (preserves handlers)

**Warning signs:**
- Console shows "MaxListenersExceededWarning"
- Click/hover events stop working after filtering
- Multiple event handlers fire for single click

**Source:** CLAUDE.md lines 108-124 document this known pitfall.

### Pitfall 2: Vue Reactivity with Sets

**What goes wrong:** Changes to Set contents don't trigger Vue re-renders even with watchers.

**Why it happens:** Vue 2.7 tracks object/array mutations but not Set/Map mutations.

**How to avoid:**
```typescript
// WRONG - Vue won't detect change
selectedIds.value.add(id)

// RIGHT - Create new Set to trigger reactivity
selectedIds.value = new Set([...selectedIds.value, id])
```

**Warning signs:**
- UI doesn't update after Set.add()/delete()
- Watchers don't fire on Set changes
- Need to watch both Set reference AND size

**Source:** CLAUDE.md lines 126-137.

### Pitfall 3: Color-By Type Detection Edge Cases

**What goes wrong:** Assuming all numbers are numeric type, when categorical IDs might be numbers (e.g., mode: 1, 2, 3).

**Why it happens:** `typeof value === 'number'` is syntactically correct but semantically wrong for categorical IDs.

**How to avoid:**
- Check if attribute has < 15-20 unique values → probably categorical
- Check if all values are integers in small range (1-10) → probably categorical
- Provide YAML override for ambiguous cases (even though type is auto-detected, allow manual override)

**Warning signs:**
- Transport mode IDs (1=car, 2=bike) showing gradient instead of discrete colors
- Integer categories getting sequential coloring
- Too many legend entries for what should be numeric

### Pitfall 4: Comparison Mode Color Conflicts

**What goes wrong:** Baseline data shows in color-by colors, making comparison mode unclear.

**Why it happens:** Not checking `showComparison` flag before applying color-by logic.

**How to avoid:**
```typescript
if (props.showComparison) {
  // Baseline: always gray (no color-by)
  if (isBaselineData) {
    return StyleManager.getInstance().getComparisonBaselineColor()
  }
  // Filtered: apply color-by only to filtered data
  return getColorByColor(dataRow)
} else {
  // No comparison mode: apply color-by to all data
  return getColorByColor(dataRow)
}
```

**Warning signs:**
- Baseline and filtered data indistinguishable in comparison mode
- User confused about what's filtered vs baseline
- Color legend doesn't match visible colors

**Source:** User requirement "baseline stays gray, filtered data gets color-by colors".

### Pitfall 5: Histogram Binning with Color-By

**What goes wrong:** Histogram bars stack categories from different bins, creating confusing overlaps.

**Why it happens:** Histogram groups by bin (x-axis), color-by groups by attribute (color), combining creates 2D grouping.

**How to avoid:**
- For categorical color-by: create separate trace per category (stacked or grouped bars)
- For numeric color-by: color entire bar by average/median attribute value in bin
- Clearly document behavior in tooltip/legend

**Warning signs:**
- Histogram with 20+ multicolor bars becomes unreadable
- User can't tell which color corresponds to which bin
- Tooltip shows confusing aggregated values

### Vue 2.7 Reactive State with ref()

```typescript
// Source: Vue.js official docs - Reactivity Fundamentals
// https://vuejs.org/guide/essentials/reactivity-fundamentals.html
import { ref, computed } from 'vue'

// Dashboard state
const colorByAttribute = ref<string>('')
const colorByOptions = ref<Array<{ attribute: string; label: string; type: string }>>([])

// Computed derived state
const hasColorBy = computed(() => colorByAttribute.value !== '')
const colorByType = computed(() => {
  if (!hasColorBy.value) return null
  const option = colorByOptions.value.find(opt => opt.attribute === colorByAttribute.value)
  return option?.type || 'categorical'
})
```

### Color Legend Data Preparation

```typescript
// Source: MapCard.vue lines 34-46 (ColorLegend integration)
interface LegendData {
  title: string
  type: 'categorical' | 'numeric'
  items?: Array<{ label: string; color: string }>  // For categorical
  minValue?: number  // For numeric
  maxValue?: number  // For numeric
}

const legendData = computed((): LegendData | null => {
  if (!colorByAttribute.value) return null

  const attribute = colorByAttribute.value
  const isCategorical = detectIsCategorical(attribute)

  if (isCategorical) {
    const sortedValues = getSortedUniqueValues(attribute)
    const colorMap = styleManager.buildCategoricalColorMap(sortedValues)
    return {
      title: toTitleCase(attribute),
      type: 'categorical',
      items: sortedValues.map(value => ({
        label: String(value),
        color: colorMap.get(value)!
      }))
    }
  } else {
    const [min, max] = getDataRange(attribute)
    return {
      title: toTitleCase(attribute),
      type: 'numeric',
      minValue: min,
      maxValue: max
    }
  }
})
```

## Open Questions

1. **Histogram color-by behavior for categorical attributes**
   - What we know: Histograms bin by numeric attribute (x-axis), color-by adds second grouping dimension
   - What's unclear: Should bars be stacked (showing category distribution per bin) or grouped side-by-side?
   - Recommendation: Stacked bars for categorical, single colored bar (by average value in bin) for numeric. Document in card-specific logic.

2. **Pie chart with numeric color-by attribute**
   - What we know: Pie charts show categorical data (slices = categories), color-by might be numeric
   - What's unclear: Does numeric color-by make sense for pie charts?
   - Recommendation: Ignore color-by for pie charts when it's numeric (pie chart already groups by its column, which is categorical). Show warning or default color.

3. **YAML migration path for existing dashboards**
   - What we know: MapCard has per-layer colorBy config (layer.colorBy: main_mode)
   - What's unclear: Do we deprecate layer-level colorBy or support both?
   - Recommendation: Support both with precedence: dashboard-level colorByAttribute overrides layer-level colorBy when present. Add deprecation warning in console.

4. **"None" option placement in dropdown**
   - What we know: User wants "None" option to disable color-by
   - What's unclear: Should "None" be first option (top of list) or last?
   - Recommendation: First option (top) so it's easy to reset. Use empty string '' as value for "None".
